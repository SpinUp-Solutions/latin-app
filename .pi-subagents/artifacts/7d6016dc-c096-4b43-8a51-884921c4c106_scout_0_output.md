### Canonical admin route protection

A new evaluation endpoint should therefore be a Next admin route using `verifyAdminAccess`, rather than calling the existing callable directly from the evaluation page.

## Architecture

The student grading flow is:

```text
TranslationGradingExercise
  → useTranslationGrading
  → Firebase callable gradeTranslationFn
  → shared/openai/translation-grading.ts
  → shared OpenAI singleton
```

Autocomplete follows:

```text
Admin vocabulary UI
  → Firebase callable autocompleteWord
  → shared/openai/autocomplete.ts
  → shared OpenAI singleton
```

The admin dashboard follows:

```text
/admin/(shell) route
  → AdminShell
  → client page wrapped with withAdminAuth
  → useAdminApi
  → /api/admin/*
  → verifyAdminAccess
  → Firebase Admin SDK / Firestore
```

For an admin-only evaluation suite, preserve that second architecture: server authorization must occur before invoking shared AI functions. Evaluation cases/runs can be stored via `adminDb`; collections intended to be server-only should also receive explicit deny rules rather than relying on the fallback rule.

Tests are Jest/Testing Library for UI and route units, with Playwright reserved for broader acceptance flows.

## Review Findings

- **high:** `functions/src/index.ts:21-26, 67-72, 113-116` — all AI callables require authentication only, not admin role. An evaluation suite must not expose batch/model experimentation through these callables without stronger authorization.
- **high:** `proxy.ts:3-9` — `/admin/*` middleware is a no-op. `withAdminAuth` is only client-side; every evaluation API route must independently call `verifyAdminAccess`.
- **medium:** `shared/openai/translation-grading.ts:211-219, 262-269` — grading calculates cost internally but drops it from the success response, preventing accurate persisted cost comparisons.
- **medium:** `shared/openai/client.ts:7-14` — hard-coded model constants and a singleton client make multi-model or mocked evaluations less convenient.
- **medium:** `firestore.rules:67-73` — unspecified collections are directly readable/writable. A new evaluation collection could accidentally be client-accessible unless explicitly denied.
- **medium:** `shared/openai/translation-grading.ts:235-245` — prompts interpolate unbounded user text directly; batch suites need case-size/count limits and concurrency/rate controls.
- **low:** `shared/openai/translation-grading.ts:243-280` and `shared/openai/autocomplete.ts:299-488` — extensive logging may expose evaluation inputs/outputs and create noisy batch logs.
- **low:** Empty `src/app/api/admin/ai/*` directories may mislead implementation; there is no existing Next AI route to extend.

## Residual Risks

- No existing persisted evaluation dataset, run schema, golden-answer format, scoring rubric, or history UI was found.
- No tests directly cover shared OpenAI modules or Firebase callable AI authorization.
- Live-model tests will be nondeterministic and costly; unit tests should mock execution, with live validation opt-in.
- Grade quality cannot be reduced safely to exact string comparison; expected grades need tolerance/ranking and qualitative fields need explicit rubric/manual review.
- Batch execution needs timeouts, concurrency limits, partial-failure persistence, and idempotent run identifiers.
- Existing grading response parsing trusts schema-conforming JSON after `JSON.parse`; semantic validation is limited.
